# セブンブリッジ 3D — 要件定義書

バージョン: 1.0（2026-08-09 凍結）
本書がゲームルール・技術構成の単一の正である。実装契約（.claude/contracts/）は本書を参照する。

---

## 1. プロダクト概要

- ブラウザで動作するトリプルA品質の3Dセブンブリッジ（トランプゲーム）
- **GitHub Pages のみで完結**（サーバーコードなし・完全無料）
- 2〜6人の通信マルチプレイ（WebRTC P2P / ルームコード制）
- UI言語: 日本語

## 2. ゲームルール仕様

### 2.1 基本
- 使用カード: **ジョーカーなしの52枚**
- プレイ人数: 2〜6人
- 各ラウンド開始時に各プレイヤーへ **7枚** 配り、残りは山札。**捨て札の場は空で開始**（2026-08-10 変更: 開始時のめくり札を廃止。最初の捨て札は最初の手番プレイヤーが作る）
- ディーラー（配り手）: 初回はルーム順の先頭。**2ラウンド目以降は直前ラウンドの勝者（上がったプレイヤー）が親になる**（2026-08-09 ユーザー指定で変更）。流局時は親継続。最初のツモはディーラーの左隣から
- 手番の流れ: **山札から1枚ツモ** → （任意: メルド公開・付け札）→ **1枚捨てて終了**
  - 捨て札の場から通常のツモはできない。捨て札の取得はポン/チーのみ（DECISION D3参照）

### 2.2 メルド（役）
| 種類 | 条件 |
|---|---|
| シークエンス | 同スートの連続する3枚以上（例: ♠4-♠5-♠6）。A-2-3 可、Q-K-A 可、**K-A-2 のような A をまたぐラップも可**（2026-08-10 変更: 循環連続。重複なし・同スート最大13枚） |
| グループ | 同ランク3枚以上（スート重複なし、最大4枚） |
| 単独の7 | **7は1枚単体でメルドとして公開できる** |

- 単独の7は「未確定メルド」。付け札により **同スート隣接カード（6/8側へ連続）→シークエンス化**、または **他スートの7→グループ化** のどちらかに成長する。方向が確定したら以後はその種類として扱う

### 2.3 付け札（ローカルルール①）
- **自分がメルドを1つ以上公開した後でなければ付け札できない**（ポン/チーで公開したメルドもカウントする）
- 付け札は自分の手番中（ツモ後〜捨て札前）に、場の**誰のメルドに対しても**可能
- シークエンスへは両端の連続カード、グループへは同ランクの残りスートを追加できる

### 2.4 ポン/チー（ローカルルール②）
- 誰かが捨て札をした直後、他のプレイヤーは鳴きを宣言できる:
  - **ポン**: **どのプレイヤーの捨て札でも**可。手札の同ランク2枚と合わせてグループを公開
  - **チー**: **直前のプレイヤー（自分の上家）の捨て札のみ**可。手札の同スート連続2枚と合わせてシークエンスを公開
- **ポンはチーに優先**する。複数のポンが競合した場合は捨てたプレイヤーから時計回りで近い方が優先
- 鳴き待ちウィンドウ: 捨て札後 **10秒**（2026-08-09 5秒から変更。鳴ける可能性のあるプレイヤー全員がパス/不能ならば即時短縮）
- **鳴き機会の秘匿**（2026-08-09 追加）: 鳴きの選択UI・カウントダウンは**鳴けるプレイヤー本人にのみ**表示する。他のプレイヤーには「誰かが鳴けること」を示す表示を出さない（情報漏洩防止。非対象者には通常の間として見える）
- 鳴いたプレイヤーは取得カードを含むメルドを**即時公開**し、その後1枚捨てて手番終了。**手番は鳴いたプレイヤーに移り**、間のプレイヤーは飛ばされる（麻雀式）
- メルド未公開のプレイヤーもポン/チー自体は可能（鳴いた時点でメルド公開者となり、以後付け札が解禁される）
- 取得した捨て札はメルドに使わなければならない（手札に入れることは不可）

### 2.5 ラウンド終了と失点
- 誰かが手札を出し切ったら（最後の1枚を捨てる・メルド/付け札で使い切るのいずれも可）**上がり**、ラウンド即終了
- 山札が尽きたら**流局**: その時点で全員が手札の失点を計上する
- 失点計算（ローカルルール確定値）: **A=1点、2〜10=額面どおり、J=11点、Q=12点、K=13点**。上がったプレイヤーは0点
- 手札に残ったカードの合計がそのラウンドの失点

### 2.6 ゲーム進行と勝敗（ローカルルール③）
- ルーム作成時に**ラウンド数を指定**（1〜20、デフォルト4）
- 指定ラウンドを消化し、**合計失点が最も少ないプレイヤーの勝ち**。同点は同着
- **スコア票**: 「ラウンド × プレイヤー」の失点マトリクス＋累計行を、ゲーム中いつでもモーダルで参照可能。各ラウンドの誰が何点失点したか・そのラウンドの合計・累計を表示
- **スコア票の時点累計**（2026-08-11 追加）: 各ラウンド行に「そのラウンドの失点」と「そのラウンド終了時点の累計」の両方を表示する（例: セル内に `12｜計34` の2段/併記。形式は視認性優先で設計）

## 3. 技術構成

| 項目 | 選定 |
|---|---|
| 言語 | TypeScript（strict） |
| ビルド | Vite（GitHub Pages 用に base 設定） |
| 3D描画 | Three.js |
| 通信 | Trystero（WebRTC P2P、公共シグナリング）。ルームコード（英数6桁）で入室 |
| テスト | Vitest（ルールエンジンは純粋TSでユニットテスト必須） |
| デプロイ | GitHub Actions → GitHub Pages |

### 3.1 アーキテクチャ原則
- **ルールエンジンは純粋TS**（DOM/Three.js/通信に非依存）。全ゲームロジックは `(state, action) => state` の決定的遷移で表現し、ユニットテストで検証する
- **ホスト権威モデル**: ルーム作成者（ホスト）のクライアントがルールエンジンを実行する唯一の主体。他ピアはアクション要求を送り、ホストが検証・適用して結果を配信する
- **視界フィルタ**: ホストは各ピアに「自分の手札＋公開情報（場のメルド・捨て札・他人の手札枚数・山札残数）」のみを送る。他人の手札は配信しない
- 状態同期は差分ではなく**フィルタ済み全量スナップショット**（プリモーテムE5: ズレ対策。データ量は十分小さい）
- 切断・再入室: 同じルームコードで再接続したピアにはスナップショットを再送して復帰させる。**ホスト切断時はゲーム続行不能を全員に通知して終了**（v1ではホスト移譲なし）
- **人数は開始時確定**（2026-08-10 変更）: ルーム作成時に人数上限を指定しない（席上限は6）。ホストが開始した時点の参加者数でゲーム人数が確定（2人以上で開始可）
- **共有導線**（2026-08-10 追加）: 待機ルームに共有ボタン（Web Share API、非対応はコピー）と URL 参加リンク（`?room=コード` で参加フローへ直行）を用意し、アプリを離れずに招待できる
- **バックグラウンド耐性**（2026-08-10 追加）: タブ/アプリ切替から復帰時に接続を自動回復（visibilitychange で再アナウンス/再購読）。モバイルOSの完全停止は復帰時回復でカバー
- **公開ルーム一覧ロビー**（2026-08-10 追加）: 作成時に「公開する」を選ぶとロビーの公開ルーム一覧（ホスト名・現在人数・ラウンド数）に表示されワンタップ参加可。P2Pの固定ロビーチャネルでの広告で実現（サーバーレス維持）。広告にコード・ホスト名・人数・ラウンド数以外を載せない

### 3.2 3D表現（トリプルA品質の定義）
- カード: 角丸ジオメトリ、スート/ランクはテクスチャアトラス（Canvas生成でアセット外部依存なし）、表裏マテリアル、影
- 卓: フェルト質感の円卓/多角卓、環境光＋スポットライト、トーンマッピング
- アニメーション: 配札・ツモ・捨て札・メルド公開・付け札・ポン/チー演出・上がり演出をすべて補間アニメーションで表現（即時テレポート禁止）
- カメラ: 自席視点を基本に、ラウンド開始/終了時の演出カメラワーク
- 席レイアウト: 2〜6人で自動配置
- パフォーマンス: ミドルスペックPCで60fps目標、モバイルでも動作すること
- **3D空間への直接D&D**（2026-08-09 ユーザー要望で追加）: 捨て札・メルド公開・付け札は、3D卓上の対応する場所（捨て札の山・場のエリア・対象メルド）へのドロップで行える。ドラッグ中はドロップ可能な3D領域が視覚的に分かること
- **3D席名表示**（同上）: 3D卓上の各席に誰の手札/席か分かる名前表示（ビルボードラベル等）を出す
- **メルドUIの被り解消**（同上）: 2DのメルドリストUIが3Dビューを覆って見づらい問題を解消（コンパクト化・退避・トグル等、3D側の視認性を優先）
- **手札の並び替え**（2026-08-09 ユーザー要望で追加）: 手札はドラッグ&ドロップで自由に並び替え可能（マウスとタッチの両対応）。並び順はローカルの表示状態であり、エンジンの手札集合には影響しない。ツモで増えた/出して減った後も、ユーザーが決めた相対順序を保持する
- **モバイル縦画面（ポートレート）対応**（2026-08-09 ユーザー要望で追加）: スマホ縦持ちでプレイ可能であること。縦画面ではカメラ・UI レイアウトを縦長ビューポートに最適化（手札・鳴きボタン・HUD が指で操作できる配置とサイズ、タッチ操作前提）。横画面・PC も従来どおり動作。リサイズ/回転で動的に追従する

### 3.3 画面構成
1. **タイトル/ロビー**: 名前入力、ルーム作成（人数上限・ラウンド数設定）/ ルームコード入力で参加
2. **待機ルーム**: 参加者一覧、ホストがゲーム開始
3. **ゲーム画面**: 3D卓 + HUD（手番表示、鳴きボタン[ポン/チー/パス]、残り時間、山札残数）
4. **スコア票モーダル**: いつでも開ける失点マトリクス
5. **リザルト画面**: 最終順位とスコア票

## 4. 品質基準（L1）
- `npm run build` 成功（警告0は不要、エラー0）
- `npx tsc --noEmit` クリーン
- `npm test`（Vitest）グリーン — ルールエンジンのテスト必須項目:
  - メルド判定（シークエンス/グループ/単独7/A絡み境界/ラップ不可）
  - 単独7の成長（シークエンス化・グループ化・方向確定後の制約）
  - 付け札の資格（メルド未公開者の拒否、鳴き後の解禁）
  - ポン/チーの資格判定（チーの上家限定、ポン優先、競合解決）
  - 失点計算（A=1, J=11, Q=12, K=13）
  - 上がり判定・流局・ラウンド遷移・スコア集計
  - 2人戦/6人戦の境界

## 5. 主要DECISION（要ユーザー確認事項は▲印）
- D1: 通信=Trystero サーバーレスP2P（ユーザー確定）
- D2: ジョーカーなし・失点 A=1/額面/J=11/Q=12/K=13（ユーザー確定）
- D3: ▲ 捨て札の通常取得（手番でのツモ代わり）は**不可**とした。ポン/チーが捨て札取得の唯一の手段（麻雀式ルールとの整合を優先）
- D4: ▲ 流局時は全員の手札を失点計上（上がり者なし）
- D5: ▲ ホスト切断時はゲーム終了（v1ではホスト移譲を実装しない）
- D6: 鳴きウィンドウは10秒固定（全員パス/不能で即短縮。2026-08-09 に5秒から変更）
- D7: 3Dアセットはすべてプロシージャル生成（外部アセット依存なし、Pages配信が軽量）
