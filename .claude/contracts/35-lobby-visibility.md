# 契約35: R38 — 公開ルーム可視性の端末差の根本修正

## 症状（2026-08-12 ユーザー報告）
モバイルで公開ルームを作成すると、他端末のルーム検索に「引っかかる端末と引っかからない端末」が
同時に存在する（ペア依存・再現性が揺れる）。

## 根本原因の分析
広告は「nostrリレーでピア発見 → WebRTC データチャネルで配送」の2段で届く。どちらの段にも欠陥があった:
1. **WebRTC 段: TURN が無い** — trystero/simple-peer の既定は STUN 2本のみ。モバイル回線の
   CGNAT/対称NAT 同士のペアは STUN だけでは直結できず、シグナリングは成功しても
   データチャネルが開かない → 「その端末にだけ広告が届かない」ペア依存の症状に直結
   - さらに **trystero が渡す iceServers は simple-peer に無視される**構造だった
     （simple-peer が RTCPeerConnection へ渡すのは opts.config のみ。trystero は rtcConfig を
     opts トップレベルへスプレッドするため、`rtcConfig: { config: {...} }` と包む必要がある）
2. **nostr 段: 購読のサイレント死** — リレーが購読を静かに切る/スリープ復帰で切れると、
   そのロビーは既存ピア以外の新規ホストを二度と発見できない（リロードまで直らない）

## 対策
1. `trysteroTransport.ts`: `rtcConfig: { config: ICE_CONFIG }` で STUN 4本 + **TURN
   （Open Relay/metered 無料公開・ベストエフォート）** を注入。死んでいても候補が増えるだけで無害
2. `LobbyLink.enableSelfHeal(factory)`: **ピア0かつ無活動45秒でトランスポートを作り直す**
   （10秒間隔点検 + online/visibilitychange で即点検）。閲覧側・広告側（ホスト）の両方に結線。
   ピアが居る間は広告は WebRTC 上を流れるため作り直さない
3. ロビー診断に「ロビーピア n」を追加（リレー接続と WebRTC 接続を切り分けて報告できる）

## 検証
- ユニット: 自己修復2件（無活動→再生成→広告再受信 / ピア存在中は再生成しない）追加、net 24件 green
- 実機2タブ: 公開ルーム掲載・診断表示（リレー8/8・ロビーピア1）を確認
- 実機のモバイルペア再現はユーザーに依頼（TURN 経路はネットワーク依存のため）
